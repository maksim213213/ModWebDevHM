# Bonus 3 — Размышления

### 1. Почему `createSlice` позволяет писать `state.items.push(...)`, хотя Redux требует иммутабельности?

Под капотом Redux Toolkit использует **Immer**. Редьюсер работает с черновиком (draft —
Proxy), который записывает все «мутации». По завершении Immer создаёт новый иммутабельный
объект состояния, не трогая старый. То есть код выглядит мутабельным, но в стор попадает
новый неизменяемый объект.

### 2. Стоит ли хранить в Redux данные, загруженные с реального API?

`filter` — это клиентское UI-состояние, ему место в Redux. А загруженные todo — это
**серверное состояние** со своим жизненным циклом (кэш, устаревание, рефетч). Для него лучше
использовать RTK Query или React Query: они дают кэширование и обработку загрузки/ошибок «из
коробки». Клиентское состояние — в Redux, серверные данные — в кэш-слое.

### 3. Что сломается, если два компонента вызывают `useSelector(state => state.todos.items)`, а один из них ещё и `useSelector(state => state.todos.filter)`?

Ничего не сломается. `useSelector` сравнивает результат по ссылке (`===`) и
перерисовывает компонент только при изменении выбранного значения. Компоненты с `items`
ререндерятся при изменении `items`, но не `filter`; компонент с `filter` — ещё и при смене
фильтра. Проблема возникнет, только если селектор возвращает новую ссылку каждый раз
(например `items.filter(...)` прямо в селекторе) — тогда `===` всегда ложь и идут лишние
ререндеры. Решение: возвращать стабильные ссылки и мемоизировать через `createSelector`.
